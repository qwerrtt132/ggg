# Orchestrate mixed-provider agents through one event log

Build a single-process Python backend that runs one lead agent and a few bounded workers as asyncio tasks, with one writer owning a shared task board. Agents exchange typed Task and Artifact records, not replayed chat transcripts. Multi-agent coordination is a hypothesis to test: controlled studies find debate rarely beats a single agent with voting at equal compute, and multi-agent setups win mainly on independent, parallel subtasks, so benchmark every design against a single-agent baseline. Guard the four failure families (vague delegation, lost context, unverified "done", loops) with a hard step cap, token and time budgets, a verifier-gated completion check, and a repeat and stall detector. Keep provider keys on the server only, encrypted at rest with a master key stored outside the data directory, and never return them to the browser. Stream all live state over one Server-Sent Events (SSE) connection backed by an append-only SQLite event table whose sequence numbers double as SSE event IDs, and send human input as ordinary POSTs. The evidence is weakest for the UI layer: every UI-architecture source is a search excerpt because the primary documentation sites failed to load, so pin versions and re-verify before building.

**Tags.** **[Primary]** means the notes record a fetch of the source itself. **[Excerpt]** means a search snippet or secondary summary only. **[Inference]** means my synthesis from the notes, which no source states. I folded the notes' finer tags ([E], [P], [F], [S], and the Requirement and Recommendation wording labels) into these three tiers. Recommendations below are inferences unless tagged otherwise.

## Recommendations for the builder

1. **Topology: orchestrator-worker with a single writer.** One lead plans and synthesizes. Each worker gets an objective, an output format, a tool list, and boundaries. Only the lead or a board service writes shared state. Start with one agent and add workers only for independent subtasks. [Primary for the pattern; Inference for the app rule]
2. **Do not default to free-form group chat or debate.** [Excerpt]
3. **Messages: in-process typed records with A2A-style field names.** Use Task `{id, contextId, status.state, inputs, artifacts}` and pass large outputs as references. Do not run A2A HTTP servers in v1, but keep the names so you can externalize later. [Inference]
4. **Keys: server-only, write-only, encrypted at rest.** Use Fernet. Store the master key in a 0600 file outside the data directory, with the OS keyring as an optional backend. Put a key-version byte in each record. Default to memory-only keys. [Inference, on Primary OWASP and pyca sources]
5. **Live UI: SSE for server-to-browser, POST for input, one stream per page.** Write the SSE framing yourself on a streaming response. Do not depend on the newly added FastAPI SSE class until its version is verified. [Inference; Excerpt for FastAPI]
6. **Guardrails: layered budgets, verifier-gated done, loop detection.** Details in the failure-mode section. [Inference on Primary and Excerpt]
7. **Localhost hardening, which no note covers.** Bind to 127.0.0.1, validate the Host and Origin headers, and require a per-launch token on key endpoints. A malicious page can otherwise send requests to a local server. [Inference]
8. **Re-verify the flagged primary sources** in the table below before writing UI or framework-dependent code.

## Communication: orchestrator-worker with references, not transcripts

Anthropic's research system uses orchestrator-worker. A lead agent plans, spawns subagents that search in parallel, and receives condensed findings ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). **[Primary]** The same post reports that agents use **roughly 4x** chat tokens and multi-agent systems **roughly 15x**, and that the design suits high-value parallel work but not tasks with many dependencies, "such as most coding work." **[Primary]** Its **90.2%** gain over single-agent Opus 4 comes from an internal eval that no one has replicated. **[Primary, internal eval]** Anthropic's "Building effective agents" post advises finding "the simplest solution possible." **[Primary]** ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents))

The frameworks differ mainly in where state lives. AutoGen's SelectorGroupChat keeps one shared thread and picks speakers with an optional selector function or a model call. It falls back to the previous speaker, or else the first participant, if all attempts fail. **[Primary, summarized source]** ([AutoGen source](https://raw.githubusercontent.com/microsoft/autogen/main/python/packages/autogen-agentchat/src/autogen_agentchat/teams/_group_chat/_selector_group_chat.py)) Every participant reads the whole thread, so context cost grows with headcount, and a termination condition is required. **[Inference]** OpenAI Agents SDK handoffs are one-to-one transfers exposed as `transfer_to_<agent>` tools, and the receiving agent sees the full history by default. **[Primary, summarized]** ([OpenAI Agents SDK](https://raw.githubusercontent.com/openai/openai-agents-python/main/docs/handoffs.md)) LangGraph keeps typed state with explicit channels, uses `Send` for per-branch payloads, and uses `Command` for combined routing and update. **[Primary, summarized]** ([LangGraph types](https://raw.githubusercontent.com/langchain-ai/langgraph/main/libs/langgraph/langgraph/types.py)) Typed state is easier to inspect and checkpoint, so I would use that shape. **[Inference]**

A2A defines a Task with `taskId` and `contextId`, status states including `TASK_STATE_INPUT_REQUIRED`, Artifacts, and AgentCards for discovery. Push notifications are delivered at least once, so receivers must be idempotent. **[Primary, but only about 100,000 of 158,000 characters were read and the enum spellings come from a summary]** ([A2A spec](https://raw.githubusercontent.com/a2aproject/A2A/main/docs/specification.md)) The MCP draft covers agent-to-tool messaging and says that "the spec defines none" for agent-to-agent communication. **[Primary, draft]** ([MCP draft](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/draft/basic/index.mdx)) The layering that follows is MCP for each agent's tools and A2A-style Task objects for agent-to-agent work. **[Inference]**

Context is the scarce resource. Anthropic's lead saves its plan to external memory because context beyond about **200,000 tokens** gets truncated, and subagents store large outputs externally and return lightweight references. **[Primary]** Chroma tested 18 LLMs and found reliability fell as input grew, even on simple tasks. **[Excerpt]** ([Chroma](https://trychroma.com/research/context-rot)) Cognition argues for sharing full agent traces, while Anthropic argues for narrow task boundaries. The notes leave this tension unresolved. **[Excerpt]** ([Cognition](https://cognition.ai/blog/dont-build-multi-agents)) I would pass a structured state object (goal, facts, plan, decisions, artifact IDs with summaries) and give each worker only the inputs its objective needs. Trigger compaction on a token threshold, not on turn count. **[Inference]**

Human input has three documented models. A2A's input-required state resumes on the same task ID. **[Primary]** LangGraph's `interrupt()` requires a checkpointer and re-runs the node from its start. **[Primary]** Gates such as OpenAI's `on_handoff` or AutoGen's `selector_func` can block a transfer or speaker choice. **[Primary]** I would model human input as an `input_required` task state that resumes a pending future, and validate the POST body against a schema before anything is saved. **[Inference]**

## Failure modes: four families need layered guardrails

The most systematic public taxonomy is MAST, which defines 14 failure modes in three categories, built from annotated traces across seven frameworks. **[Excerpt, arXiv pages did not fetch]** ([MAST v2](https://arxiv.org/html/2503.13657v2)) Verification failures are the most consistent finding. An IBM and Berkeley analysis of 310 SRE traces names incorrect verification as the strongest predictor of failure. **[Excerpt, secondary]** ([HF blog](https://huggingface.co/blog/ibm-research/itbenchandmast)) Anthropic's own early failures included **spawning 50 subagents for simple queries** and vague delegation that caused duplicate work. **[Primary]** Cognition's example of split subtasks producing incompatible outputs is also excerpt-only. **[Excerpt]**

Controlled studies mostly find that debate does not reliably beat self-consistency or majority voting at equal compute. Smit et al. (ICML 2024) reached this result, and a 2025 study of five debate methods across nine benchmarks confirmed it. **[Excerpt]** ([ICML 2024](https://proceedings.mlr.press/v235/smit24a.html); [arXiv 2502.08788v3](https://arxiv.org/html/2502.08788v3)) Agents favor agreement over challenging flawed reasoning, and a weaker agent can drag the group down. **[Excerpt]** ([arXiv 2509.05396v2](https://arxiv.org/html/2509.05396v2)) A Google, DeepMind, and MIT study found added agents hurt most on sequential, tool-heavy tasks, and one summary cites drops of **up to 70%**. The versions disagree on configuration count (180 vs. 260) and fit (R² 0.513 vs. 0.373). **[Excerpt; verify before citing]** ([arXiv 2512.08296](https://arxiv.org/abs/2512.08296)) Sycophancy priors raised accuracy by **10.5% absolute** across six open models in one 2026 paper. **[Excerpt; verify]** ([arXiv 2604.02668](https://www.alphaxiv.org/abs/2604.02668)) For the builder, this means defaulting to a single agent with voting. If you add critique, make the reviewer rubric-driven and told to find errors, use heterogeneous models, collect independent first answers, and cap rounds. **[Inference]**

Parallel writers overwrite each other, and agents sharing one repository hit git lock contention. **[Excerpt, vendor guide]** ([Augment Code](https://augmentcode.com/guides/git-worktrees-parallel-ai-agent-execution)) Cognition's 2026 follow-up says that multiple agents contributing intelligence while writes stay single-threaded is the pattern that works. **[Excerpt]** ([Cognition 2026](https://cognition.com/blog/multi-agents-working)) I would enforce one writer per resource, use compare-and-swap on a base hash for file writes, and give code agents separate git worktrees. **[Inference]** No source evaluates locks or task claims for LLM agents. **[Gap]**

Frameworks ship caps, but they fire late. AutoGen's termination conditions run after each response and include max-message, token-usage, timeout, and external terminations. **[Excerpt, v0.4.9 docs]** LangGraph's default recursion limit is 25 steps. **[Excerpt; config placement unverified]** OpenAI's runner raises `MaxTurnsExceeded`, and a forum thread reports that catching it did not recover the final output. **[Excerpt]** Anthropic's post gives no global turn cap. It sets per-subagent budgets of **3 to 10 tool calls** for fact-finding and **10 to 15 per subagent** for comparisons. **[Primary]** These are starting points, not validated values. A fingerprint of (tool, arguments) caught stuck loops within three repetitions in one arXiv paper on terminal coding agents. **[Excerpt]** ([arXiv 2603.05344](https://arxiv.org/pdf/2603.05344)) Magentic-One's progress ledger triggers a re-plan after a stall counter, but the threshold could not be confirmed. **[Excerpt, secondhand]** ([summary](https://startdebugging.net/2026/10/what-is-magentic-orchestration-in-microsoft-agent-framework/))

I would layer the controls in this order. (1) A hard step cap per run, surfaced as a failure and never retried silently. (2) Token and wall-clock budgets via `asyncio.timeout()` and token accounting, because **token usage explained about 80% of performance variance** on BrowseComp. **[Primary]** (3) Per-worker tool-call budgets. (4) Completion only when a verifier passes, never on an agent's own claim. This follows from MAST's verification evidence. **[Inference]** (5) A repeat detector on (tool, args), plus A-B-A-B and no-op checks, escalating from hint to block to stop. (6) A progress check every N rounds, with a bounded number of re-plans. (7) A checkpoint after each step in SQLite. On startup, mark runs left in `running` as `interrupted`. Anthropic says agents resume from the point of failure, not from the start. **[Primary; the startup rule is Inference]** No note covers provider-specific errors such as rate limits, malformed tool calls, or context overflow. Normalize them into the app's own error classes. **[Inference]**

## API keys: server-side only, encrypted, never echoed

Keep provider keys out of the browser entirely. OWASP says not to store credentials in localStorage or sessionStorage, because any script on the origin can read them. **[Primary]** ([OWASP Session Management](https://github.com/OWASP/CheatSheetSeries/blob/master/cheatsheets/Session_Management_Cheat_Sheet.md)) OpenAI says keys belong in server code, never in browsers, mobile apps, or repositories. **[Excerpt]** ([OpenAI](https://help.openai.com/en/articles/5112595-best-practices-for-api-key-safety)) Anthropic says never to include a key in code or configuration files, and to prefer encrypted secret storage over dotenv files in cloud environments. **[Primary]** ([Anthropic](https://support.claude.com/en/articles/9767949-api-key-best-practices-keeping-your-keys-safe-and-secure))

Encrypt with an authenticated mode. OWASP says authenticated modes "should always be used where available," warns against custom algorithms, and says keys should not sit next to the data they protect. **[Primary]** ([OWASP Cryptographic Storage](https://github.com/OWASP/CheatSheetSeries/blob/master/cheatsheets/Cryptographic_Storage_Cheat_Sheet.md)) For a single-user app, Fernet is the lower-risk choice. It uses AES-128-CBC with HMAC-SHA256, draws IVs from a CSPRNG, and supports `MultiFernet` rotation. **[Primary, pyca source]** ([Fernet](https://github.com/pyca/cryptography/blob/main/docs/fernet.rst)) Raw AESGCM puts nonce uniqueness on you, and reusing a nonce with a key "compromises the security" of messages under that pair. **[Primary]** ([AEAD docs](https://github.com/pyca/cryptography/blob/main/docs/hazmat/primitives/aead.rst)) I would store a key-version byte with each ciphertext so the master key can rotate, and treat `InvalidToken` as a prompt to re-enter keys, not a crash, because providers let users re-issue keys. **[Inference]**

The master key is the real secret. A backup that contains both the master key and the ciphertext protects nothing, so keep them apart. **[Inference]** OWASP discourages environment variables for secrets when no managed store exists, and says keys must never be stored in plaintext. **[Primary]** OpenAI recommends loading `OPENAI_API_KEY` from the environment. **[Excerpt]** The notes only partly resolve this conflict. I would keep the master key in a 0600 file outside the data directory, accept an environment variable that points to that file, and treat the OS keyring as optional. **[Inference]** On Linux the `keyring` library needs a running Secret Service over D-Bus, and no note establishes that this works headless. **[Primary README; headless behavior unverified]** ([jaraco/keyring](https://github.com/jaraco/keyring))

No primary source compares memory-only and persisted keys. OWASP does say that restarting an app does not revoke stolen credentials, and it recommends regular rotation. **[Primary]** For a present-user app I would default to memory-only keys, offer encrypted persistence as an opt-in, and decrypt per call rather than caching plaintext in long-lived objects. **[Inference]**

For the API surface, accept the key through a write-only field and return only provider, label, last four characters, timestamps, and status. Never echo the key in a response or an error. **[Inference]** OpenAI shows the full secret only at creation and returns a redacted value afterward, which is the model to copy. **[Excerpt]** ([OpenAI service accounts](https://developers.openai.com/api/reference/resources/organization/subresources/projects/subresources/service_accounts/methods/create)) Rotation should add the new key, verify it, switch, and delete locally. Then tell the user to revoke the old key at the provider, because deleting it in the app does not revoke it. **[Inference]** Set spend limits at each provider too. Anthropic says limits "act as a safeguard against unexpected usage due to leaked keys." **[Primary]** OWASP says secrets should never be logged unless they are encrypted or masked. **[Primary]** Log provider calls as metadata only (provider, model, host, status, latency, token counts), add a redaction filter as a second layer, and check whether SDK exceptions print request headers. The notes do not answer that last question. **[Inference; Gap]**

## UI architecture: one SSE stream over one event log

Use one-way SSE for server-to-browser state. The browser reconnects automatically, and a server `id` sets `lastEventId`. **[Excerpt]** ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)) HTTP/1.1 limits connections per host to about six, and open event streams can stall other requests. One 2019 write-up reports this, and a related Chrome bug was closed as by design. **[Excerpt, dated; limit approximate]** ([textslashplain](https://textslashplain.com/2019/12/04/the-pitfalls-of-eventsource-over-http-1-1/)) HTTP/2 removes most of the limit. **[Excerpt, secondary]** ([enterno](https://enterno.io/en/s/glossary-sse)) I would multiplex all event types onto one stream per page and send human input as POSTs. WebSockets earn their complexity only for high-rate client-to-server traffic, and they do not reconnect on their own. **[Inference; MDN WebSocket page not fetched]**

Make each SSE `id` the sequence number of a row in an append-only `events` table, so a reconnecting browser can request everything after its last ID. **[Inference]** The notes say browsers send `Last-Event-ID` on reconnect, per the WHATWG spec, but that behavior was not confirmed. **[Excerpt, unverified]** Write the state row and its event in one transaction, then notify subscribers, with one writer connection per process. SQLite WAL lets readers overlap the writer, but `synchronous=NORMAL` can lose the most recent transactions on power failure. **[Excerpt]** ([SQLite WAL](https://www.sqlite.org/wal.html))

FastAPI with uvicorn is the recommended backend, because agent runs map to asyncio tasks and the framework handles JSON models. **[Inference]** Its SSE class, `EventSourceResponse` in `fastapi.sse`, is reported as added in version **0.135.0**. **[Excerpt; version from a Korean tutorial mirror, release date unknown]** ([FastAPI SSE](https://fastapi.tiangolo.com/tutorial/server-sent-events/)) Third-party `sse-starlette` has conflicting version data: 1.1.4 on PyPI and 3.4.8 in an aggregator. **[Excerpt]** Starlette's `StreamingResponse` accepts an async generator. **[Excerpt]** ([Starlette](https://www.starlette.dev/responses)) So write the `text/event-stream` framing yourself (`id:`, `event:`, `data:`, blank line). It is a few lines, and it removes the dependency on an unverified version. **[Inference]** The stdlib `ThreadingHTTPServer` works with zero dependencies, but the Python docs say it is "not recommended for production." **[Excerpt]** ([http.server](https://docs.python.org/3/library/http.server.html)) Flask is the least suitable choice for async agent runs. **[Inference]**

Run each agent as an asyncio task in one loop. Use `Task.cancel()` for cancellation and `asyncio.timeout()`, available from Python 3.11, for deadlines. **[Excerpt]** ([asyncio tasks](https://docs.python.org/3/library/asyncio-task.html)) Cancellation is not guaranteed, because code can swallow `CancelledError`, and the docs warn that this can break `asyncio.timeout()` and `TaskGroup`. **[Excerpt]** Route blocking LLM SDK calls through `asyncio.to_thread`. A thread cannot be force-killed, so rely on the SDK's request timeout. **[Inference; no SDK's threading behavior was checked]** Record timeouts and cancellations as events so the UI can show them.

Serve plain HTML with ES modules and the native `EventSource`, with no build step. Render agent output with `textContent`, never `innerHTML`, because agent output is untrusted text. **[Inference]** Use typed events such as `message`, `status`, `task_update`, and `input_request`. Mirroring LangGraph's stream modes (`updates`, `messages`, `custom`) keeps a framework pluggable later. **[Excerpt]** ([LangGraph streaming](https://docs.langchain.com/oss/python/langgraph/streaming)) Preact or Alpine pinned to an exact version is the middle path, and you should vendor the file if the app must run offline. **[Inference]**

## Design decisions and open questions

**Design decisions**

1. Topology is orchestrator-worker with one lead. Cap worker concurrency at a small number (3 to 4 is a placeholder to tune).
2. One writer owns the shared task board. Workers return Artifacts, not direct board writes.
3. Messages are in-process Task, Message, and Artifact records with A2A field names. No A2A HTTP in v1.
4. Shared context is a structured state object plus artifact references. No full-transcript replay by default.
5. The provider layer is one internal interface with two adapters: native Anthropic, and OpenAI-compatible with a user-supplied base URL.
6. Keys are server-only, write-only on input, and encrypted with Fernet. The master key lives in a 0600 file outside the data directory, with the keyring optional. Each record carries a key-version byte. Keys are memory-only by default.
7. Key metadata responses return masked values and timestamps only. Provider-call logs are metadata only, with a redaction filter.
8. The server binds to 127.0.0.1, checks Host and Origin, and requires a per-launch token on key endpoints.
9. Server-to-browser state uses one SSE stream per page, with sequence numbers as event IDs. Input and control use POST.
10. SQLite runs in WAL mode with one writer. The `events` table is both the replay log and the audit trail.
11. The frontend has no build step. It uses ES modules and `EventSource`, and renders agent output with `textContent`.
12. Guardrails are a step cap, token and time budgets, per-worker tool budgets, verifier-gated completion, and a repeat and stall detector with bounded re-plans. A restart marks running runs as `interrupted`.

**Open questions**

1. Does a multi-agent design beat a single agent with voting on our real tasks? A benchmark harness is needed before committing to the topology.
2. Which FastAPI and `sse-starlette` versions are right? Verify release dates and changelogs. The recommendation to write SSE framing directly avoids the question, if you accept it.
3. Does `Last-Event-ID` replay behave as expected in the target browsers? Verify against WHATWG and test it.
4. On headless Linux, does the Secret Service work? If not, the 0600 master-key file becomes the only path.
5. Memory-only or persisted keys? This is a user preference, and it depends on whether unattended runs must survive restarts.
6. What are the Anthropic and OpenAI-compatible API details (tool-call formats, streaming events, error and rate-limit classes)? The notes do not cover them, and the adapters depend on them.
7. When should a worker see full traces (Cognition) and when should it get a narrow brief (Anthropic)? Test both on our tasks.
8. What are the numeric thresholds for step caps, repeat counts, token budgets, and worker concurrency? No source gives validated values, so set them by measurement.
9. Do agent tools go through MCP, and is the stable MCP spec compatible with the draft the notes read?
10. Is CrewAI in scope? The notes could not check it. The default is to exclude it.
